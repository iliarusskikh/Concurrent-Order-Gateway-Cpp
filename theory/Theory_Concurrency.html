Concurrent Order Gateway · Knowledge notes

Concurrency { Shards, queues, sync }

How this pipeline stays correct under load: one owner thread per book, bounded SPSC between stages, mutex+CV inside the queues, atomics for control flags, and an explicit full-queue policy.

01

Core model

Matching cares about orderability per instrument. Two threads mutating the same price-time book without a careful protocol is a correctness bug, not a performance tweak.

The structural rule: one thread owns each book. Parallelism comes from running many symbols at once, plus concurrent ingress and publishing. Cross-thread communication is queues and a few atomics — not shared mutable LOB state.

pipeline (multi-symbol)
gateway (main / batch thread)
    │  route by symbol_id
    ├─ try_push → ingress[0] → matcher0 (engine0) → events[0] ─┐
    ├─ try_push → ingress[1] → matcher1 (engine1) → events[1] ─┼→ publisher
    └─ try_push → ingress[N] → matcherN (engineN) → events[N] ─┘
Where in this codebase

The picture above is the header comment in include/multi_symbol_pipeline.hpp. One-symbol mode is the same idea with a single shard.

02

Thread roles & shard-by-symbol

Shard-by-symbol means each instrument maps to its own ingress queue, matching engine, and outbound event queue. Orders for symbol A never touch worker B’s book.

ThreadOwnsTalks to
Gateway (batch producer) Routing by symbol_id Produces into each shard’s ingress SPSC
Matcher worker i MatchingEngine for symbol i Consumes ingress; produces into events[i]
Publisher EventLog, latency aggregators Drains all event queues; never touches books
Shard (multi_symbol_pipeline.hpp)
struct Shard {
  SpscQueue<GatewayOrder, kIngressQueueCapacity> ingress;
  SpscQueue<PublishEvent, kEventQueueCapacity>   events;
  lob::MatchingEngine                            engine;
};
  • v1 is 1:1 symbol_id → shard index (no hash collision story yet).
  • Unknown symbol_id ≥ num_symbols is counted and discarded before enqueue.
  • Matchers are spawned as joinable threads behind ThreadGuard; no detach().
Where in this codebase

MultiSymbolPipeline::run in include/multi_symbol_pipeline.hpp routes, enqueues, and joins. The consumer loop lives in run_matcher_worker (include/matcher_worker.hpp). Draining is run_publisher_multi in include/publisher.hpp.

03

Why the book stays single-threaded

The LOB assumes sequential submit: price-time priority, resting orders, and event sequences are defined for one mutator. Spreading one book across threads would require either a global lock on every submit (serializing the interesting work) or a much harder concurrent book protocol.

Sharding sidesteps that: concurrency is across symbols. Inside a shard, matching is ordinary single-threaded C++.

ApproachCorrectness costv1?
One owner thread per book Structural — no cross-thread LOB races Yes
Mutex around a shared global book Correct but serializes all symbols Rejected
Thread-pool stealing across books Easy to break FIFO / affinity expectations Rejected
shared_mutex around submit Implies shared mutable book; sharding abandoned Not needed
Invariant

Matcher i is the only thread that may call engines[i].submit. The queue mutex protects ring indices — never the LOB. Pop under lock (or after pop_wait returns), unlock, then match.

04

SPSC topology (not a free-for-all queue)

Single-Producer / Single-Consumer: exactly one thread may call push-family methods; exactly one other thread may call pop-family methods. The type does not enforce that at compile time — the architecture does.

PatternProducersConsumersUse here
SPSC11Gateway → matcher ingress; matcher → per-shard events
MPSCN1Not used in v1 (would need if many ingress threads shared one queue)
SPMC1NNot needed

Why per-shard event queues? If every matcher pushed into one shared outbound queue, that queue would be MPSC — multiple producers, one publisher. Keeping events[i] private to matcher i preserves the SPSC contract on both hops. The publisher fans in by polling each queue.

Publisher wake

One publisher must sleep until any shard has work, or until all matchers have finished. That bell is EventWake in include/event_wake.hpp: matchers call notify() after pushes (and on exit); the publisher waits on a predicate over matchers_left and pending events.

roles on each hop
ingress[i]:  gateway  (producer)  →  matcher i (consumer)   — SPSC
events[i]:   matcher i (producer) →  publisher (consumer)   — SPSC
EventWake:   matchers notify      →  publisher waits        — shared CV

Bounded rings live in include/spsc_queue.hpp. Capacities are compile-time constants (kIngressQueueCapacity / kEventQueueCapacity in matcher_worker.hpp).

05

Bounded queue API

A bounded queue has a fixed slot count. When full, push must fail, block, or drop — you pick a policy. Unbounded growth under burst load hides overload and can OOM a demo.

v1 storage is std::array<T, N> as a circular buffer (head / tail / size), synchronized with std::mutex + two condition variables. Correct and testable first; lock-free later if needed behind the same method names.

MethodBehaviorTypical caller
try_push(T&&) If room: move in, notify; return true. If full: leave item, return false. Gateway ingress; matcher → events (drop+count)
push_wait(T&&, stop) Block until space or stop; return false if stopped while full. Optional blocking / teaching mode
try_pop(T&) If non-empty: move out; return true. Else false. Publisher drain loops
pop_wait(T&, stop) Block until item or stop; return false on shutdown with empty queue. Matcher idle wait
wake_all() Notify both CVs so blocked waiters can exit. Shutdown after flipping stop flags
try_push / pop_wait (spsc_queue.hpp)
bool try_push(T&& item) {
  {
    std::lock_guard<std::mutex> lock(mu_);
    if (size_ == N) return false;
    buf_[tail_] = std::move(item);
    tail_ = next(tail_);
    ++size_;
  }  // unlock before notify
  cv_not_empty_.notify_one();
  return true;
}

template <typename StopPred>
bool pop_wait(T& out, StopPred&& stop) {
  std::unique_lock<std::mutex> lock(mu_);
  cv_not_empty_.wait(lock, [&] {
    return size_ > 0 || stop();
  });
  if (size_ == 0) return false;  // stopped and drained
  out = std::move(buf_[head_]);
  head_ = next(head_);
  --size_;
  lock.unlock();
  cv_not_full_.notify_one();
  return true;
}
Move hand-off

Orders cross threads by move, not shared ownership. After a successful try_push(std::move(go)), the producer’s object is moved-from. Never hold a reference into a ring slot across threads — always move out into a local T.

Why not bare std::queue? It is not thread-safe, unbounded by default, and scatters lock/CV policy across call sites. SpscQueue<T, N> owns the ring, the mutex, and the wake protocol in one place.

06

Mutex, unique_lock, CV, spurious wakeups

The queue’s critical section is only “touch ring indices / size / slot.” Prefer RAII locks so exceptions and early returns unlock safely.

TypeUse when
std::lock_guard<std::mutex> Simple scope lock; no mid-function wait (try_push / try_pop).
std::unique_lock<std::mutex> Required by condition_variable::wait; can unlock before notify.

std::condition_variable lets a thread sleep until another signals that shared state may have changed. Always pair with the mutex that protects that state.

  • wait(lock, pred) — atomically unlock + sleep; on wake, re-lock and re-check pred.
  • notify_one() — enough for a true SPSC waiter.
  • notify_all() — shutdown / shared wake paths (wake_all, EventWake).
predicate wait (mandatory)
// NEVER: cv.wait(lock); if (empty()) ...   // race + spurious wake
// ALWAYS: wait until the predicate is true
cv_not_empty_.wait(lock, [&] {
  return size_ > 0 || stop();
});

// Equivalent manual form:
while (size_ == 0 && !stop()) {
  cv_not_empty_.wait(lock);
}

Spurious wakeups are allowed by the standard: a thread may leave wait without a matching notify. The predicate (or while-loop) is mandatory, not pedantry. The same pattern appears in EventWake::wait — the publisher re-checks “any pending events or all matchers done.”

Lost wake vs predicate

If the producer fills a slot and notifies before the consumer starts waiting, a bare wait can hang forever. Predicate wait returns immediately when size_ > 0 already holds. Update protected state under the lock, then notify.

07

Atomics for flags and counters

Use atomics for cross-thread scalars that are not part of the mutex-protected ring: stop flags, live worker counts, drop counters. Do not mix atomics and mutex casually on the same ring fields — v1 keeps head/tail/size as plain integers under the lock.

UseTypeWhereTypical order
Ingress finished std::atomic<bool> ingress_done_ multi_symbol_pipeline.hpp store release; load acquire in matcher stop predicate
Matchers still alive std::atomic<int> matchers_left_ pipeline + publisher acq_rel decrement; acquire in publisher exit check
Drop / reject counts std::atomic<uint64_t> ingress / events / unknown symbol relaxed increments for stats
practical memory orders
// after enqueuing the batch:
ingress_done_.store(true, std::memory_order_release);
for (auto& shard : shards_) shard->ingress.wake_all();
wake_.notify();

// matcher stop predicate (matcher_worker.hpp):
auto stop = [&] {
  return ingress_done.load(std::memory_order_acquire);
};

// full queue at gateway:
ingress_drops_.fetch_add(1, std::memory_order_relaxed);

Practical guidance: relaxed for independent counters; acquire/release when a flag write must become visible before another thread acts on “we’re stopping.” Default seq_cst is safe if you are unsure — correctness over cleverness.

08

Backpressure: drop+count vs block

Bounded SPSC means the producer will eventually hit capacity. Backpressure is the explicit choice when that happens — instead of unbounded RAM growth. CLI / file ingress has no socket to disconnect, so v1 chooses between block and drop+count.

StageProducerConsumerPressure signal
Ingress Gateway Matcher worker Shard ingress SPSC full
Events Matcher worker Publisher Per-shard event SPSC full
PolicyBehaviourv1 default?Trade-off
Drop + count try_push fails → discard, bump atomic Yes Keeps the producer responsive; loses work; overload is visible
Block push_wait until space (or stop) Optional / teaching Preserves every item; can stall the whole pipeline; hides overload as “slowness”
Disconnect Close client / reject session N/A (no TCP) Natural for sockets; revisit if TCP ingress lands
ingress drop (multi_symbol_pipeline.hpp)
if (!shard.ingress.try_push(std::move(go))) {
  ingress_drops_.fetch_add(1, std::memory_order_relaxed);
}
event-path drop (matcher_worker.hpp)
if (!events.try_push(std::move(pe))) {
  event_drops.fetch_add(1, std::memory_order_relaxed);
}
if (wake != nullptr) wake->notify();
Symmetric fuse

Capacity on ingress without capacity on events just moves the hang one hop later. Prefer the same policy family on both hops. If the event queue is full and the matcher blocks, it stops popping ingress → ingress fills → the gateway feels pressure that looks like “matching is slow.”

  • A dropped ingress order never reaches the LOB — no partial book mutation.
  • A dropped publish event means the book already mutated; the audit trail is incomplete — still count it.
  • Do not format logs on the failed try_push hot path beyond the atomic bump.
09

Shutdown order

Wrong join order hangs or loses wakes. The multi-symbol batch path documents a fixed sequence:

  1. Enqueue the whole batch (gateway / main thread as sole ingress producer).
  2. Store ingress_done_ = true (release), then wake_all() on every ingress queue.
  3. Notify EventWake so the publisher is not stuck if matchers exit quickly.
  4. Each matcher drains remaining ingress via pop_wait, pushes leftover events, decrements matchers_left_, notifies wake, and events.wake_all().
  5. Publisher drains all event queues until matchers_left_ == 0, then final-drains and exits.
  6. Join matchers, then join publisher (ThreadGuard).
stop producing → wake → join (pipeline)
ingress_done_.store(true, std::memory_order_release);
for (auto& shard : shards_) {
  shard->ingress.wake_all();
}
wake_.notify();

for (auto& m : matchers) m->join();
publisher.join();
Order of stop

Stop producing first, then wake and join matchers, then join the publisher after event queues drain. Joining the publisher while matchers still push — or flipping ingress_done_ without wake_all — leaves a worker blocked in pop_wait forever.

BugHow it shows upFix
Shutdown hang Flag false but no notify; worker blocked in wait Notify all relevant CVs after flipping the flag
Join while still producing Publisher joined before matchers finish pushing Matchers first (or wait on matchers_left_), then publisher
Lock-order deadlock Nested locks across queues / stats One mutex per queue; atomics for counters; no nested queue locks
10

Pitfalls & decisions

✕

Sharing a MatchingEngine across threads

Undefines LOB correctness. Shard ownership is the safety net — do not “just add a mutex around submit” as the design.

✕

Two producers on one “SPSC”

If two threads push the same queue, the SPSC contract is broken. Serialize ingress on one thread or design MPSC deliberately.

✕

Waiting without a predicate

Spurious wakeups and notify-before-wait both break bare wait. Always re-check empty / full / stop flags.

✕

Busy-spin on try_pop forever

Burns a core. Matchers use pop_wait; the publisher sleeps on EventWake when idle.

✕

Silent drop with no counter

Looks like a matching bug (“where did my fills go?”). Always expose ingress and event drop counts.

✕

Holding the queue mutex across matching

Pop, unlock, then submit. Holding the ring lock across LOB work stalls the gateway for no benefit.

Decision · ownership

Shard-by-symbol + one matcher thread per book + dedicated publisher. Rejected: thread-pool stealing across books; one mutex-protected global book; shared_mutex around submit.

Decision · queues

Mutex-backed bounded SpscQueue<T, N> with try_push / pop_wait / wake_all. Per-shard event queues keep both hops SPSC; EventWake fans the publisher in. Rejected: lock-free ring in v1; unbounded std::queue + scattered locks; single shared MPSC outbound queue.

Decision · sync & pressure

Per-queue mutex + CV; atomics for ingress_done_, matchers_left_, and drop counters. Default full-queue policy: try_push + drop + count on ingress and events. Optional push_wait for demos. Rejected as default: always-block (hides overload); busy-spin idle.
