Concurrent Order Gateway · Knowledge notes

Architecture { Pipeline & decisions }

How orders move through threads in this repository, which pieces are reused from the LOB / MDS companions, and which design choices are locked for v1.

01

Purpose

The LOB project already matches orders for one instrument on one thread. The MDS project already pushes market data over TCP. This project fills the gap between them: a concurrent ingress and fan-out path into matching.

Core idea

Keep each book single-threaded for correctness. Put concurrency in the plumbing — queues, sharding, publisher — not inside the match loop.

02

Pipeline

v1 data path
scenario / CLI
      │
      ▼
 Gateway (this thread in MultiSymbolPipeline::run)
      │  route by symbol_id
      ├─ ingress[0] ─► matcher 0 (engine 0) ─► events[0] ─┐
      ├─ ingress[1] ─► matcher 1 (engine 1) ─► events[1] ─┼─► publisher
      └─ ingress[N] ─► matcher N (engine N) ─► events[N] ─┘
                                                         │
                                                         ▼
                                              EventLog + latency_stats

Each ingress[i] and events[i] is an SPSC queue. Sharing one event queue across matchers would make that hop MPSC and break the SPSC contract used elsewhere.

03

Scenario DSL

Ingress is a text file loaded by scenario_loader.hpp (CLI: ./gateway path [num_symbols]). Assertions live in C++ tests — the loader only feeds orders.

LineMeaning
NEW id SIDE TYPE qty price Limit/market order; default symbol_id = 0
… SYM n Same, routed to shard n
# comment / blank Ignored
CANCEL … Recognized by the parser but skipped in v1 (matcher path is submit-only)
scenarios/multi_symbol_demo.txt
NEW 1 BUY  LIMIT 10 100 SYM 0
NEW 2 SELL LIMIT 10 100 SYM 0
NEW 1 BUY  LIMIT 5  50  SYM 1
NEW 2 SELL LIMIT 5  50  SYM 1

Examples: scenarios/one_symbol_demo.txt, scenarios/multi_symbol_demo.txt. Field order is qty then price (same as LOB DSL).

04

Thread roles

RoleOwnsCode
Gateway Routing, enqueue, drop counters multi_symbol_pipeline.hpp (run)
Matcher i MatchingEngine for symbol i matcher_worker.hpp
Publisher Formatting, EventLog, publish-side latency publisher.hpp

Shutdown order: finish producing → set ingress_done → wake ingress queues → join matchers (they decrement matchers_left) → publisher drains events → join publisher.

Design decisions

TopicChoiceRationale
ShardingOne matcher thread per symbolBook never shared across threads
QueuesMutex + CV SPSC, capacity fixed at compile timeReadable; tested; enough for this scale
EventsPer-shard event SPSCPreserves SPSC; publisher uses EventWake
Full queueDrop + atomic counterOverload is observable
IngressScenario file / CLIIsolates concurrency from networking
DialectC++17Threads, atomics, chrono, templates
08

Rejected alternatives

✕

One shared book + big mutex

Works in demos but teaches locking theater instead of ownership boundaries. Sharding removes the need to lock the book.

✕

N matchers → one shared event queue

That hop becomes MPSC. v1 keeps one event SPSC per matcher.

✕

Lock-free matching book in v1

Easy to get wrong; weakens the “shipped and tested” bar. Optional later behind the same worker API.
